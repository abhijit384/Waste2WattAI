## Workflow

Existing authenticated scan and private upload validation → inference flag choice. With inference disabled, a new uploaded scan transitions to FAILED with ANALYSIS_UNAVAILABLE and the state machine ends successfully; this intentional state does not enter the failure queue. Duplicate terminal events are ignored. With inference explicitly enabled in a later authorized deployment, the path is ValidateImage → AnalyzeWithBedrock → ValidateClassification → EvaluateRecoveryPathways → CalculateEnvironmentalImpact → PersistAnalysis → UpdateScanStatus.

The Python handler also supports an internal HealthCheck diagnostic that imports the deployed handler/dependencies and returns READY plus the inference flag before creating any AWS clients or invoking a model.

The initial Stage 1 pre-deployment review found that this safe disabled branch was not present in the earlier baseline. The user then explicitly approved the revised diff. The deployed workflow adds upload validation, an execution claim/duplicate guard, an `analysisEnabled` choice, a ScanStatus `unavailable` action, and a successful terminal state for intentional disabled analysis. A live test exposed that the Choice followed `ValidateImage`, causing the disabled Lambda guard to fail. The Choice now precedes the analysis Lambda. After the separately authorized `typing_extensions` package repair, HealthCheck returns `READY`; the next controlled upload's state machine succeeded through the unavailable branch.

The object event must bind to the persisted owner's scan and exact S3 version. A conditional execution claim admits only one processing execution. A retry of image validation by the same execution is safe; a competing execution exits without inference. Terminal COMPLETED/FAILED records are never reprocessed. The atomic scan/counter reservation permits one initial model attempt. Cached validated classification resumes without another invocation. Inference errors/timeouts retain the reservation; automatic replay is forbidden. Results are schema-validated and persisted before the final COMPLETED transition. Partial storage/status failures remain explicit; existing failure handling does not manufacture a result.

Task outputs contain status only. Caught failures retain sanitized codes; existing terminal failure events continue reporting to the retained failure queue. Generic service failures may display PROCESSING_FAILED if persistence is unavailable; specialized persisted codes are INVALID_IMAGE, INVALID_MODEL_OUTPUT, ANALYSIS_UNAVAILABLE and AI_LIMIT_EXCEEDED. Queue duplicates from the existing two reporting paths remain possible and are not changed by this task.
